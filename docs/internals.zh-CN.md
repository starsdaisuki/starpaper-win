# StarPaper for Windows — 原理与实测

[English](internals.md) · **简体中文**

面向想读代码或想改它的人。README 里只留了用户需要知道的部分，踩过的坑和实测数字在这里。

---

## 1. 挂到桌面层

`src/desktop.cpp`

给 `Progman` 发那个没有文档的 `0x052C` 消息，逼 Explorer 在桌面图标背后生成一个
`WorkerW` 窗口，然后 `SetParent` 把自己塞进去。壁纸就在图标下面、桌面背景上面。

⚠️ Win10 1803+ 有两种桌面结构，查 `Progman` 有没有 `WS_EX_NOREDIRECTIONBITMAP`
来区分 —— 新结构里 `WorkerW` 是 `Progman` 的**子窗口**，老结构里是**兄弟窗口**，
找法完全不同。这是这段代码里唯一容易踩的坑。

这个机制是公开的 Windows 技巧，不是谁的专有实现。

## 2. 播视频：frame-server 模式

`src/player.cpp`

解码交给 Media Foundation 的 **Media Engine**（`IMFMediaEngine`），
但**呈现由我们自己做**：给 Media Engine 一个 `IMFDXGIDeviceManager` 而
**不给** `MF_MEDIA_ENGINE_PLAYBACK_HWND`，它就不再自己往窗口上画，
改为等我们调 `TransferVideoFrame` 把当前帧拷进我们的纹理。

我们这边持有一个 D3D11 设备和一条交换链，渲染线程的循环只有三步：

```
OnVideoStreamTick(&pts)     ← 有没有新帧（判据是 pts 变了没有，不是返回值）
TransferVideoFrame(back, &src, &dst, &border)
Present(1, 0)
```

**为什么值得自己写这几十行**：`TransferVideoFrame` 的源矩形是**归一化坐标 0~1**，
目标是**我们自己创建的纹理上的像素** —— 整条链路里没有任何一处会替我们做 DPI 换算。
让 Media Engine 自己排版的那条路（`UpdateVideoStream`）在 150% 缩放下怎么传都对不上。

附带好处：帧经过我们的手，之后加亮度 / 对比度 / 模糊只是一个 shader 的事。

依赖仍然只有系统 DLL：D3D11、DXGI、Media Foundation 都是 Windows 自带的。
既不需要外挂 mpv（78~111 MB），也不需要 WPF `MediaElement`（背 .NET 运行时）。

## 3. 填满屏幕：裁剪表达在源上，不在目标上

```
屏幕 3024x1890 (1.6:1)  ×  视频 1920x1080 (16:9)

视频更宽 → 左右各切掉一些，上下一点不切
sw  = 1080 x 1.6 = 1728          （源里与屏幕同比例的最大矩形）
ox  = (1920 - 1728) x 0.5 = 96   （focus=0.5 居中）
src = 96/1920 .. 1824/1920 = 0.050 .. 0.950   ← 交给 TransferVideoFrame
dst = 0,0 .. 3024,1890                        ← 铺满整块 surface
```

再乘上 `zoom`（源矩形按倍数收窄）和 `focusX/focusY`（源矩形往哪边挪）。
归一化的源矩形没有单位可以被误解，**所以这条路上不存在 DPI 歧义**。

> ⚠️ **不要退回到「让目标矩形比窗口大、多出来的让窗口剪掉」那条路。**
>
> 那种做法要求 Media Engine 和我们对目标坐标系的理解完全一致，而 150% 缩放下并不一致。
> 三种假设都试过，互相矛盾：传物理像素画面放大约 1.5 倍；传逻辑像素缩到 2/3、
> 右下露出系统壁纸；传 `NULL` 让它自己算仍然放大且顶部多出黑边。
> 声明 `PER_MONITOR_AWARE_V2` 也不改变任何一条。而窗口几何本身经诊断确认完全正确
> —— 问题在那个黑盒里，绕不过去，只能不用它。
>
> 另一个更早的坑：最早是「放大窗口 + `SetWindowRgn` 剪裁」，几何算得分毫不差，
> 但 Media Engine **不会自己跟上窗口 resize**，画面照样是错的。

> 📏 **验收方式**：这类偏差**用真实壁纸完全看不出来** —— 两张 focus 相反的截图肉眼
> 完全一样。必须用带刻度的合成图案，把边界落点当数字来对。工具和固定流程在
> [`../tools/`](../tools/)。上面那组参数的实测结果：
>
> ```
> x=5% 青线   预测 0.0     实测 6     Δ +6.0
> x=95% 青线  预测 3024.0  实测 3019  Δ -5.0     （线本身 6px 宽 x1.75 缩放）
> 10% 网格线  预测 840.0   实测 840   Δ +0.0
> ```

关掉「填满屏幕」就退回保持比例加黑边：源取全图，目标按比例缩放后居中，
四周由我们自己 `ClearRenderTargetView` 刷黑。

## 4. 调色：默认参数下整条 shader 链根本不建

参数全默认时帧还是由 Media Engine 直接写进后台缓冲，一点额外开销都没有。
只要动了任何一个参数才切到这条路：

```
Media Engine ──TransferVideoFrame──▶ 中间纹理
                                        │
                          1~4 趟全屏 pass（按需组合）
                          调色 → 锐化 → 降采样 → 横向模糊 → 纵向模糊
                                        ▼
                                后台缓冲的目标矩形 ──▶ Present
```

模糊半径大的时候会**先降采样再模糊**：4K 上半径 60 直接做要 240 次采样，
降 6 倍之后 9 次就够，而模糊本来就要丢高频，结果看不出区别。
降采样那一趟必须是 box filter 而不是单次双线性 —— 后者只平均 2×2 个 texel，
从 3024 缩到 504 会漏掉 8/9 的像素，混叠出来是一道道很淡的水平条纹。

`d3dcompiler_47.dll` 是运行时 `LoadLibrary` 取的，不进链接期依赖。
万一某个精简系统上没有，结果只是调色不生效，程序照常播放。

## 5. 设置窗口与可视化取景

预览里那个白框就是**真正会显示在桌面上的那一块**，框外压暗的部分会被裁掉。
直接拖框选构图，滚轮缩放，桌面**实时**跟着变。

> ⭐ 预览框和桌面裁剪调用的是**同一个函数** `FramingRect()`（`main.cpp`），
> 所以两者不可能对不上。这也是为什么可视化选框必须排在 frame-server 之后做：
> 底层不准的时候，界面只会跟着一起骗人。
>
> 实测（3024x1890 / 150% 缩放 / 1920x1080 测试图案）：框宽占底图 **89.99%**
> （预期 90%），左右边距 4.97% / 5.04% —— 亚像素级吻合。

⚠️ 界面上踩过的坑：**per-monitor v2 进程里，`SystemParametersInfoW` 返回的
`lfMessageFont` 已经是当前 DPI 的字号了，不能再乘一遍缩放**，否则 150% 下字大 1.5 倍，
按钮文字放不下、说明文字被截尾。要按 DPI 取字体应该用 `SystemParametersInfoForDpi`。

## 6. 遮挡暂停默认是关的

被窗口盖住时暂停能省 CPU，但恢复播放要重新起播，Win+D 切回桌面会顿一下才动。
所以默认不暂停，想要的人在托盘菜单里勾。

## 7. 多显示器与投屏

| 场景 | 会发生什么 | 怎么处理 |
|---|---|---|
| 串流时改主显示器分辨率 | `WM_DISPLAYCHANGE` | 重建窗口并重新贴合（已实测） |
| 启用虚拟显示器（如 Sunshine 的 Zako Display Adapter） | 多出一块屏 | 那块屏拿到自己的窗口和播放器，是完整画面而不是半张 |

⚠️ 早期版本是「一个窗口铺满所有屏的包围盒」，那样多屏下一张画面会被拉伸横跨两块屏，
每块各看到一半。**这是改成每屏一个窗口的原因。**

代价是每块屏各解码一次。Wallpaper Engine、Lively、mpv 方案付的都是这个代价；
想省掉得放弃系统的 windowed 呈现、自己写 D3D11 共享纹理，代码量翻倍以上，暂时不值。

## 8. 排查：状态挂在窗口标题上

托盘窗口（`StarPaperTray`，从不显示）的标题实时反映内部状态：

```
StarPaper screens=1 playing=1 paused=0 usr=0 lock=0 opt=0 fill=1
          src=50,0..950,1000 dst=0,0..3024,1890 f=50/50 z=100 fr=634
```

- `src` 是**源上的归一化裁剪矩形**，写成千分比（`50,0..950,1000` = 左右各裁 5%）
- `dst` 是**交换链上的目标矩形**（letterbox 时会内缩）
- `fr` 是累计画出去的帧数 —— **「画面在不在动」的唯一硬证据**

`GetWindowTextW` 就能读到，不用写日志文件。

⚠️ 别拿 CPU 占用反推「到底暂停没暂停」：同一状态实测能在 9%~18% 之间跳。
单轮采样同样不可信 —— 稳态 4 轮里 CPU 量到过 11.7% 和 26.8%，帧率却稳定在 60。

## 9. 实测代价

3024x1890 屏 / 150% 缩放 / 一段 4K60 H.264 壁纸，稳态 4 轮 × 8 秒：

| | |
|---|---|
| 帧率 | 59.8 fps（视频就是 60fps，pts 去重后一帧不多画） |
| CPU | 22.3% 单核 |
| 内存 | 140~146 MB 工作集 |

1080p30 的图案则是 30.0 fps / 约 7% 单核 / 109 MB。

> 试过两种「省掉多余帧」的节流，**都更差，别再试**：
> waitable swapchain 把帧率压到 60.0 但 CPU 涨到 15.6%~20.8%；
> `QueryPerformanceCounter` 掐表 + `Sleep(2)` 直接掉到 38.4fps —— Windows 默认定时器
> 精度 15.6ms，`Sleep(2)` 实际睡掉一整个刷新周期。`pts` 去重本身就已经够了。

### 别拿虚拟机里的数字当参考

同一段 4K60 壁纸，在 Apple Silicon 上的 Parallels / Windows 11 ARM64 里是
**32.8%（4 核归一）/ 约 420 MB**，比上面那张表高一个量级。不是软件变重了 ——
是 **Apple Silicon 的 VM 没有硬件视频解码引擎**（GPU 计数器里只有 `engtype_3d`，
没有 `engtype_VideoDecode`），4K60 H.264 全靠 CPU 软解。Parallels / VMware Fusion /
UTM 都一样，DXVA 在 ARM 上不映射到 GPU 硬件解码器；UTM 更差，Windows 侧目前连
3D 加速都没有。

⭐ **真正该看的是宿主侧**：guest 内那个百分比会严重低估代价。同一时刻量宿主的
`prl_vm_app`：**4K60 吃掉宿主 1.78 个核心**（VM 空转基线只有 0.9%），
而 guest 内只显示 28.4%。多出来的是帧穿过虚拟化显示管线的开销。
**要在 VM 里长期挂，用 1080p30**：宿主 178.4% → **85.1%（−52%）**。
降帧率 −37%、降分辨率 −42%，两者叠加最优。

同环境下还有一个反直觉的实测：**x64 版（Prism 模拟）37.7%，原生 ARM64 版 32.8%，
只差 13%。** 原因是 Windows on ARM 的系统 DLL 是 **ARM64X 混合二进制** ——
x64 进程加载的 `msmpeg2vdec.dll`（H.264 软解码器）、`MFPlat.dll`、`d3d11.dll`
内部本来就是 ARM64 原生执行，Prism 只转译应用自己那几千行。所以**原生化能省的是
应用自己的开销，省不到解码那个大头**。
